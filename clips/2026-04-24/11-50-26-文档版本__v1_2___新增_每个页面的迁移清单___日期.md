1. 背景与目标
Minerva（运营后台）目前基于 Koa + Prisma + UmiJS 构建，与 sitin-next 的 Fastify + Raw SQL + Vite 技术栈不统一。迁移目标：
- 统一技术栈，降低维护成本
- 复用 sitin-next 已有的基础设施（plugin-pg、plugin-jwt、plugin-redis）
- 获得 Fastify 的性能优势
- 统一前端构建工具链（Vite + React Router + Ant Design 6）

---

数据库访问      │ Prisma 6（ORM）                       │ Raw SQL + server-plugin-pg

5.2 页面迁移通用模板
所有页面都按以下模板迁移，保证一致性：
1. 创建 src/pages/XXX/index.tsx 文件
2. 从 UmiJS 的 useModel + useAccess → Zustand + 自定义 hook
3. API 调用从 @umijs/max request → httpClient（已封装）
4. ProTable / ProForm 尝试保留，如不兼容 antd 6 则降级为 Table/Form
5. 路由注册到 App.tsx 的 <Routes> 中
6. 权限检查用 <RequirePermission> 包裹
7. 对照老系统做页面 UI / 数据一致性验证

6. 困难与风险
🔴 高风险
- Prisma → SQL 改写量大 — 200-300 查询点，应对：逐模块迁移 + 对照验证
- SQL 手写 bug — Prisma 自动处理 NULL/类型转换，应对：严格对齐老项目 + 单测
- ChatConsole 的腾讯云 IM SDK — React 19 兼容性未知，应对：先做 POC
🟡 中风险
- UmiJS 隐式功能替换 — 已有 ProtectedRoute + Zustand 验证
- Ant Design 5→6 — 向前兼容，ProComponents 需逐页面验证
- 复杂页面（UserManagement XL、DataAnalysis XL、PWADataboard XL）— 逐 Tab/模块拆分
🟢 低风险
- Zod Schema 迁移 — 直接复制
- 简单页面（Home、Lovia、CallFeed 等）— 标准 CRUD 模式
